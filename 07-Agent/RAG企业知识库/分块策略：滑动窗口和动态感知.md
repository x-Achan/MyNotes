
### 策略一：固定窗口滑动分块

固定窗口滑动分块的核心思路是，在保证分块大小相对稳定的同时，通过内容重叠和自然语言边界回退，尽量减少上下文丢失。整个处理过程以解析后的页面为基本单位，逐页读取文本，每一页独立执行分块，这样生成的每个 Chunk 都能明确关联到一个物理页码和该页的章节标题，方便后续回答时进行来源引用和原文定位。处理某一页时，先从文本起始位置向后截取配置长度的内容；如果截取位置还没有到达页面末尾，就不会立即在这个位置硬切，而是向前回溯一定范围，优先寻找段落换行，其次寻找普通换行、句号、问号、感叹号、分号、逗号和空格等自然边界，从而降低句子被从中间切断的概率。如果限定范围内没有合适边界，才按照固定长度直接截断。生成一个 Chunk 后，下一个 Chunk 不会直接从上一个 Chunk 的结尾开始，而是向前回退一段重叠内容，步长等于窗口大小减去重叠大小。这样同一句话或同一段上下文即使位于切分边界附近，也会出现在相邻的两个 Chunk 中，能够降低检索时因边界切分造成的信息缺失。分块完成后，系统为每个 Chunk 分配全局递增编号，保留页码和章节标题，并粗略估算 Token 数量，为后续 Embedding 长度控制提供参考。这个策略的优势是实现简单、行为稳定、对新闻、小说、日志和大段连续文本具有较好的通用性，而且每个 Chunk 的大小比较均匀；它的不足是只理解文本长度和标点，不真正理解标题层级、表格、代码块和章节语义，并且由于坚持逐页处理，标题和正文、命令和参数、句子的前后部分如果刚好跨越物理页面，仍会被拆到不同 Chunk 中。因此从面试角度可以概括为：固定窗口策略使用“固定长度保证稳定性、滑动重叠保证上下文连续性、自然边界回退改善可读性、逐页处理保证来源可追溯性”，是一种通用且可预测的基础分块方案。

### 策略二：结构感知分块

结构感知分块的核心思路是优先利用文档自身的标题和章节结构保留完整语义，只有当一个章节过长时，才退化为固定窗口切分。处理开始后，系统按照文档顺序遍历所有页面和文本行，通过 Markdown 标题、中文章节标题、中文序号以及多级数字编号等特征判断某一行是否为标题，同时持续维护当前章节标题、当前章节正文以及章节开始页码。遇到普通正文时，将内容继续累积到当前章节；遇到新标题时，先把此前积累的正文保存为一个独立章节，然后将新标题设置为后续正文的上下文，并记录新章节开始的物理页码。这个过程允许同一个章节自然跨越多个 PDF 页面，因此可以解决逐页固定窗口中“标题在上一页、正文在下一页”的部分问题。章节提取完成后，系统再根据配置的 Chunk 大小进行第二层判断：如果整节内容没有超过限制，就完整保留为一个 Chunk，使标题及其正文保持在同一个语义单元中；如果章节内容过长，就把这一节临时交给固定窗口策略继续拆分，利用窗口重叠和自然断点控制每个子块的长度。所有最终 Chunk 会重新获得连续编号，并继承章节标题、章节起始页和 Token 估算等元数据。这个策略适合技术文档、操作手册、规范、论文和知识库说明，因为这类文档的标题层级本身就表达了语义边界；相比单纯按照字符数切分，它生成的 Chunk 通常主题更集中，检索结果也更容易携带正确的章节上下文。它的限制是高度依赖标题识别质量，如果文档没有规范标题、标题被 PDF 解析错误或标题格式不在识别规则中，切分质量就会下降；另外，当前设计只记录章节起始页，当一个章节跨越多页时只能定位到起始页，无法完整描述覆盖页码范围，较短章节在达到保存条件前还可能与后续章节合并。面试时可以将它概括为：结构感知策略采用“先恢复章节结构、优先保持语义完整、超长章节降级为滑动窗口、保留章节元数据用于检索增强”的分层处理方式，在结构化文档中通常比纯固定窗口拥有更好的语义完整性。


## 策略一：固定窗口滑动分块

这个策略的核心思想是：**按照固定长度切分文本，并保留一定的重叠内容，同时尽量选择自然语言边界作为切分位置。**

实现流程：

1. **逐页处理**
    
    依次读取解析结果中的每个页面，每一页单独分块。这样生成的 Chunk 一定属于某个明确的物理页面，可以直接记录页码和章节标题，方便检索结果溯源。
    
2. **按固定窗口截取**
    
    从页面文本开头开始，每次尝试截取长度为 `chunkSize` 的内容。例如配置为 500 个字符，就先计算当前起点之后第 500 个字符的位置。
    
3. **寻找合适的切分边界**
    
    如果第 500 个字符不是页面末尾，就从该位置向前回溯一定范围，寻找更自然的断点。优先级依次是：
    
    ```
    段落边界
    → 普通换行
    → 句号、问号、感叹号
    → 分号、逗号
    → 空格
    → 固定长度硬切
    ```
    
    这样可以减少一句话被从中间截断的情况。
    
4. **增加重叠内容**
    
    生成当前 Chunk 后，下一个 Chunk 会向前回退 `chunkOverlap` 个字符。
    
    例如：
    
    ```
    chunkSize = 500
    chunkOverlap = 100
    ```
    
    理论步长就是：
    
    ```
    500 - 100 = 400
    ```
    
    相邻 Chunk 共享约 100 个字符，能够减少边界位置的信息丢失。
    
5. **防止死循环和尾部重复**
    
    如果因为寻找自然断点导致下一个起点没有向前推进，就直接从当前结束位置继续。到达页面末尾后立即停止，避免最后一段内容被重复生成。
    
6. **补充 Chunk 元数据**
    
    每个 Chunk 保存：
    
    ```
    全局Chunk编号
    文本内容
    所属物理页码
    页面章节标题
    估算Token数量
    ```
    

这个策略的优点是实现简单、输出块大小稳定，适合新闻、小说、日志等连续文本。缺点是只感知字符和标点，不理解真正的章节层级，而且逐页处理会让跨页句子、命令和段落被拆开。

面试时可以概括为：

> 固定窗口滑动分块通过固定长度控制 Chunk 大小，通过重叠窗口保留边界上下文，再通过向前寻找段落和句子边界改善文本完整性。当前实现逐页处理，因此来源页码非常准确，适合作为通用的基础切分策略。

## 策略二：结构感知分块

这个策略的核心思想是：**优先按照标题和章节结构切分，尽量让一个 Chunk 表达一个完整主题；只有章节过长时，才使用固定窗口继续拆分。**

实现流程：

1. **按照文档顺序遍历内容**
    
    系统依次处理解析后的所有页面，再逐行检查每一页的文本。处理过程中持续维护：
    
    ```
    当前章节标题
    当前章节正文
    当前章节起始页
    ```
    
2. **识别标题行**
    
    根据常见标题格式判断一行是否为标题，例如：
    
    ```
    # 标题
    ## 标题
    第一章 系统介绍
    第2节 数据处理
    一、项目背景
    1. 系统架构
    1.2 数据处理
    1.2.3 向量检索
    ```
    
    同时，如果解析阶段已经识别出了页面章节标题，也会将其作为当前章节标题。
    
3. **积累章节正文**
    
    普通文本行会持续追加到当前章节中。因为遍历过程不会在页面结束时强制保存章节，所以一个章节可以跨越多个物理页面。
    
    例如：
    
    ```
    第5页：3.1 系统架构 + 前半部分正文
    第6页：后半部分正文
    ```
    
    两页内容可以共同组成“3.1 系统架构”这一节。
    
4. **遇到新标题时保存上一节**
    
    当识别到新的标题时，说明前一个章节结束。系统先保存已经积累的正文，再将新标题设置为当前章节标题，并记录标题所在页为新章节的起始页。
    
    标题本身单独保存在 `sectionTitle` 中，不重复放进正文。
    
5. **根据章节大小决定是否继续切分**
    
    提取出章节后，判断章节正文是否超过配置大小：
    
    ```
    章节长度 ≤ chunkSize
        → 整节作为一个Chunk
    
    章节长度 > chunkSize
        → 交给固定窗口策略继续拆分
    ```
    
    这样既保留了短章节的完整语义，又能避免超长章节超过 Embedding 模型的输入限制。
    
6. **超长章节降级到固定窗口**
    
    超长章节会复用第一个策略，按照固定窗口、重叠内容和自然语言边界切成多个子块。
    
    这些子块仍然继承原章节的：
    
    ```
    章节标题
    章节起始页
    ```
    
7. **统一生成最终结果**
    
    所有正常章节块和超长章节的子块会重新分配连续的 Chunk 编号，并补充 Token 估算信息。
    

这个策略的优点是语义完整性较高，适合技术手册、规范、论文和产品文档。缺点是依赖标题识别准确度；如果原文没有规范标题或 PDF 提取后标题格式损坏，结构切分效果就会下降。此外，当前只记录章节起始页，跨页章节无法完整表示结束页。

面试时可以概括为：

> 结构感知分块先根据标题恢复文档章节，让同一主题的正文尽量保持在同一个 Chunk 中；对于超过长度限制的章节，再降级使用固定窗口切分。这是一种“结构优先、长度兜底”的分层策略，比单纯按照字符数切分更适合结构清晰的技术文档。
