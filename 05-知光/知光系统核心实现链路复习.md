

## 一、系统定位与总体设计

知光是一个知识内容社区，当前核心业务包括：

1. 用户注册、登录与身份认证
    
2. 用户资料及头像管理
    
3. 知文草稿、文件上传、编辑、发布和权限控制
    
4. 点赞、取消点赞、收藏、取消收藏
    
5. 关注、取关、关系状态、关注列表、粉丝列表和人数
    
6. 热门 Feed、个人主页 Feed、他人主页 Feed、关注 Feed
    
7. 搜索与 AI 问答暂未实现
    

主要技术：

|技术|作用|
|---|---|
|Spring Boot|Web 服务和依赖管理|
|Spring Security + JWT|身份认证和接口鉴权|
|MyBatis + MySQL|持久化及真相源|
|Redis|验证码、令牌、计数、位图、列表和 Feed 缓存|
|Redisson|分布式锁|
|Kafka|点赞收藏明细异步落库、投影事件消费|
|Outbox + Canal|从数据库可靠发布关系和帖子事件|
|OSS|存储正文、图片和头像|
|Caffeine|Feed 页面本地缓存|

# 二、先掌握三个核心概念

## 2.1 真相源

真相源是丢失缓存后仍然可以重建数据的持久化数据。

|业务|真相源|
|---|---|
|用户|`users`|
|帖子|`know_posts`|
|关注关系|`following`|
|点赞收藏明细|`like_record`|
|待投递事件|`outbox`|

Redis 中的计数、列表、Feed 索引和页面都属于派生数据，可以通过 MySQL 重建。

## 2.2 命令模型与查询模型

系统没有让每一次查询都直接执行复杂 SQL，而是把模型分成两类：

- 命令模型：MySQL 中的业务事实
    
- 查询模型：Redis 中针对查询场景构建的投影
    

例如：

```
following
    ├── 投影为关注数和粉丝数
    ├── 投影为关注列表、粉丝列表缓存
    └── 投影为关注 Feed 的 inbox/pull 数据
```

这样可以让写业务保持清晰，同时针对不同读取场景建立不同的数据结构。

## 2.3 最终一致性

系统没有要求所有缓存与数据库在同一个瞬间完全相同，而是通过以下机制收敛：

1. 事件实时更新
    
2. 缓存未命中时从数据库重建
    
3. TTL 使旧数据自然淘汰
    
4. 定时对账修复计数偏差
    
5. 消费者重复执行时保持幂等

# 三、系统整体链路

```
flowchart LR
    Client[客户端] --> Security[Spring Security]
    Security --> API[Controller]
    API --> Service[业务 Service]

    Service --> MySQL[(MySQL)]
    Service --> Redis[(Redis)]
    Service --> OSS[(OSS)]
    Service --> Kafka[(Kafka)]

    MySQL --> Outbox[(outbox 表)]
    MySQL --> Binlog[MySQL Binlog]
    Binlog --> Canal[Canal]
    Canal --> CanalTopic[Kafka canal-outbox]

    CanalTopic --> RelationProjection[关系投影]
    CanalTopic --> FeedProjection[帖子 Feed 投影]

    RelationProjection --> Redis
    FeedProjection --> Redis

    Redis --> FeedQuery[Feed 查询组装]
    MySQL --> FeedQuery
    FeedQuery --> Client
```

系统存在两条异步事件路线。

## 路线一：点赞收藏直接写 Kafka

```
请求
→ Redis Bitmap 改变用户状态
→ 同步发送 Kafka
→ Redis 计数增减
→ Kafka 消费者批量写 like_record
→ 定时对账修复 Redis 计数
```

适用于高频、允许最终一致的点赞收藏。

## 路线二：关系和帖子使用 Outbox + Canal

```
业务表修改 + outbox 插入
→ 同一个 MySQL 本地事务提交
→ MySQL 写 binlog
→ Canal 读取 binlog
→ Canal 发送到 Kafka
→ 消费者更新 Redis 投影和 Feed
```

适用于关注关系、帖子状态等需要可靠通知多个下游模块的业务。

# 四、认证系统

核心代码：

- `AuthController`
    
- `AuthService`
    
- `JwtService`
    
- `RedisRefreshTokenStore`
    
- `VerificationService`
    
- `RedisVerificationCodeStore`
    
- `SecurityConfig`
    

## 4.1 验证码链路

验证码分为：

- 注册 `REGISTER`
    
- 登录 `LOGIN`
    
- 重置密码 `RESET_PASSWORD`
    

Redis 使用三个 Key：

```
auth:code:{scene}:{identifier}
auth:code:last:{scene}:{identifier}
auth:code:count:{scene}:{identifier}:{date}
```

对应职责：

|Key|用途|
|---|---|
|`auth:code`|保存验证码、错误次数、最大次数|
|`auth:code:last`|控制发送间隔|
|`auth:code:count`|控制每日发送总数|

发送流程：

```
校验账号格式
→ 根据场景检查用户是否应该存在
→ 检查发送间隔
→ 每日发送数 INCR
→ SecureRandom 生成验证码
→ Redis Hash 保存验证码并设置 TTL
→ CodeSender 发送
```

校验成功后删除验证码，防止重复使用；校验失败则增加尝试次数。

## 4.2 注册和登录

注册：

```
验证服务条款
→ 标准化手机号或邮箱
→ 检查账号不存在
→ 校验注册验证码
→ BCrypt 加密密码
→ 写入 users
→ 签发 Access Token 和 Refresh Token
→ Refresh Token 的 jti 写入 Redis
```

登录支持：

- 密码登录
    
- 验证码登录
    

当密码和验证码同时存在时，当前代码优先采用密码。

## 4.3 双 Token

Access Token：

- 15 分钟有效
    
- 用于访问业务接口
    
- 不保存到服务端
    

Refresh Token：

- 7 天有效
    
- 用于换取新的 Token
    
- `jti` 保存在 Redis 白名单
    

Redis Key：

```
auth:rt:{userId}:{tokenId}
```

刷新时：

```
解析 Refresh Token
→ 校验 token_type
→ 检查 Redis 白名单
→ 撤销旧 Refresh Token
→ 签发新的 TokenPair
→ 保存新的 jti
```

这是 Refresh Token Rotation。

## 4.4 Spring Security

请求携带：

```
Authorization: Bearer access_token
```

Spring Security 完成：

1. 提取 Bearer Token
    
2. RSA 公钥验签
    
3. 校验过期时间
    
4. 将 `Jwt` 放入 `SecurityContext`
    
5. Controller 使用 `@AuthenticationPrincipal Jwt jwt`
    
6. 从 `uid` Claim 中得到用户 ID

# 五、用户资料与 OSS

## 5.1 资料更新

资料更新采用 PATCH 语义：

```
JWT 获取 userId
→ 查询当前用户
→ 检查至少提交一个字段
→ 知光号唯一性校验
→ 只更新非 null 字段
→ 回读数据库
→ 返回最新资料
```

MyBatis 动态 SQL 的意义是：没有提交的字段不参与更新。

## 5.2 头像上传

当前头像链路：

```
浏览器上传 MultipartFile
→ 后端读取文件
→ 后端上传 OSS
→ 得到公开 URL
→ 更新 users.avatar
```

## 5.3 帖子文件直传

帖子正文和图片使用客户端直传：

```
创建帖子草稿
→ 客户端请求预签名 URL
→ 服务端验证帖子归属
→ 服务端生成 objectKey 和 PUT URL
→ 客户端直接 PUT 到 OSS
→ 客户端调用 content/confirm
→ 服务端把 objectKey、ETag、大小、SHA256、URL 写入 MySQL
```

直传的价值：

- 大文件不经过应用服务器
    
- 降低应用服务器带宽和内存压力
    
- 后端只处理权限、签名和元数据
    

Feed 只返回卡片信息和图片 URL。正文 URL 只在帖子详情中返回，客户端再根据 URL 访问 OSS。

# 六、帖子生命周期

## 6.1 状态

当前代码支持：

```
draft       草稿
published   已发布
deleted     软删除
```

可见性代码目前支持：

```
public
followers
school
private
unlisted
```

实际 Feed 权限主要实现了：

- `public`
    
- `followers`
    
- 作者本人查看其他状态
    

`school` 和 `unlisted` 没有形成完整查询语义，笔记中应标为预留状态。

## 6.2 创建与发布链路

```
创建草稿
→ 雪花算法生成 postId
→ 写 know_posts
→ 写帖子 UPSERT Outbox 事件

请求 OSS 预签名 URL
→ 客户端上传文件
→ 确认文件信息

修改标题、标签、摘要、图片、可见性
→ 更新 know_posts
→ 写 UPSERT Outbox 事件

发布
→ draft 改为 published
→ 设置 publish_time
→ 写 UPSERT Outbox 事件
```

删除使用软删除：

```
status = deleted
→ 写 DELETE Outbox 事件
→ Feed 投影异步清理索引和缓存
```

## 6.3 雪花 ID

当前生成器结构：

```
41 位时间戳
+ 5 位数据中心
+ 5 位工作节点
+ 12 位毫秒内序列
```

特点：

- 单机同步方法保证线程安全
    
- 每毫秒最多生成 4096 个 ID
    
- 小于等于 5ms 的时钟回拨会短暂等待
    
- 较大回拨直接拒绝生成
    
- 返回前端时转成字符串，避免 JavaScript Number 精度丢失
    

## 6.4 帖子详情权限

```
查询帖子和作者
→ 不存在或 deleted：拒绝
→ 当前用户是作者：允许
→ published + public：允许
→ published + followers 且已关注作者：允许
→ 其他情况：拒绝
```

通过权限校验后，再补充：

- 点赞数
    
- 收藏数
    
- 当前用户是否点赞
    
- 当前用户是否收藏

# 七、点赞收藏计数系统

## 7.1 三类 Redis 数据

### 用户操作状态

```
bitmap:{metric}:knowpost:{postId}:{chunk}
```

Bitmap 的一个 bit 表示某个用户是否操作过。

分片计算：

```
chunk = userId / 32768
offset = userId % 32768
```

每个分片约 4KB，避免大用户 ID 造成巨大稀疏位图。

### 帖子计数

```
cnt:knowpost:{postId}:like
cnt:knowpost:{postId}:fav
```

### 对账索引

```
cnt:index
```

Set 成员：

```
{postId}:{metric}
```

索引集合用于随机抽样，避免使用 `KEYS` 扫描全部 Redis。

## 7.2 点赞写链路

```
检查帖子存在且未删除
→ Lua 原子读取并修改 Bitmap
→ 状态未变化：幂等返回
→ 状态变化：同步发送 Kafka
→ Kafka 发送失败：补偿 Bitmap
→ Redis 计数 INCRBY
→ 返回最新状态和计数
```

Bitmap Lua 的核心是：

```
读取当前 bit
→ 当前值等于目标值：返回未改变
→ 否则修改 bit 并返回已改变
```

因此重复点赞和重复取消不会重复修改计数。

## 7.3 Kafka 异步落库

生产者：

- Kafka Key 使用帖子 ID
    
- 同一帖子的事件进入同一分区
    
- `acks=all`
    
- 启用生产者幂等
    
- 发送时等待 Broker 确认
    

消费者：

```
批量拉取最多 500 条
→ JSON 反序列化
→ 聚合为批量数据库操作
→ 成功后手动 ACK
```

`like_record` 唯一键：

```
(user_id, post_id, type)
```

负责保证重复 Kafka 消息不会产生重复点赞明细。

## 7.4 计数读取

单个读取：

```
Redis GET
→ 命中直接返回
→ 未命中进入进程内 single-flight
→ 双重检查
→ MySQL COUNT
→ 回写 Redis
→ TTL 加随机抖动
→ 登记 cnt:index
```

批量读取：

```
Redis MGET
→ 收集缺失 postId
→ MySQL 一次 GROUP BY
→ SETNX 回填
→ 按请求原顺序返回
```

`SETNX` 可以避免数据库查询期间的新点赞被旧查询结果覆盖。

## 7.5 Feed 中的用户状态

Feed 一次返回多篇帖子，因此使用 Redis Pipeline 批量执行 `GETBIT`，得到：

- 当前用户点赞过哪些帖子
    
- 当前用户收藏过哪些帖子
    

避免每篇帖子单独进行一次网络请求。

## 7.6 对账自愈

```
定时任务
→ Redisson 分布式锁
→ 从 cnt:index 随机抽样
→ 查询 MySQL COUNT 真值
→ Lua 计算 truth-current
→ 使用 INCRBY 差值修正
```

使用差值修正是为了保留对账期间发生的并发增量。

# 八、关注系统

## 8.1 数据模型

当前真实实现采用单表：

```
following
```

核心字段：

```
from_user_id：发起关注的人
to_user_id：被关注的人
rel_status：1 有效，0 已取消
created_at：最近一次关注时间
```

唯一键：

```
(from_user_id, to_user_id)
```

一行数据同时支持：

- 我关注了谁：查 `from_user_id`
    
- 谁关注了我：查 `to_user_id`
    

笔记里的 `following + follower` 双表属于早期方案，已经不是当前代码的实际设计。

## 8.2 关注写链路

```
拒绝关注自己
→ 校验目标用户存在
→ Redis 令牌桶限流
→ INSERT IGNORE 尝试首次关注
→ 已有取消记录时执行 revive
→ 没有状态变化则幂等返回
→ 同一事务写 RelationEvent 到 outbox
→ 提交事务
```

取关：

```
令牌桶限流
→ UPDATE rel_status 1→0
→ 没变化则幂等返回
→ 同一事务写取消关注事件
```

## 8.3 令牌桶

Redis Hash 保存：

```
last
tokens
```

Lua 中使用 Redis `TIME`：

```
计算过去时间
→ 按速率补令牌
→ 不超过桶容量
→ 尝试扣除一个令牌
```

使用 Redis 时间可以避免多个应用实例之间的系统时钟差异。

## 8.4 关系状态

关注状态直接查 MySQL：

```
A 是否关注 B
B 是否关注 A
```

得到：

- `following`
    
- `followedBy`
    
- `mutual`
    

关系状态属于强业务判断，当前设计没有依赖异步缓存。

## 8.5 关注和粉丝列表

Redis 使用部分 ZSet 缓存：

```
relation:following:{userId}
relation:followers:{userId}
```

成员：

```
member = 用户 ID
score = 关注时间
```

两个特殊成员：

```
__INIT__：表示缓存已经初始化，即使列表为空
__END__：表示数据库已经没有更多数据
```

读取：

```
Redis ZSet 命中
→ 判断已缓存数量是否满足 offset+limit
→ 满足则直接分页返回
→ 不满足且没有 END
→ Redisson 加锁
→ 分批从 MySQL 加载 30 条
→ 追加到 ZSet
→ 加载到目标位置或读到结尾
```

发生关注或取关后，消费者删除相关的两个部分缓存：

```
关注者的 following 缓存
被关注者的 followers 缓存
```

下一次读取时从 MySQL 懒重建。

部分缓存不能简单地对新用户执行 `ZADD`，否则缓存中间插入新数据会改变已有分页位置。

## 8.6 关注数和粉丝数

Redis String：

```
ucnt:{userId}:followings
ucnt:{userId}:followers
```

读取：

```
Redis 命中直接返回
→ 未命中查询 following 表 COUNT
→ 写回 Redis
→ TTL 加随机抖动
→ 登记 ucnt:index
```

关系事件到达时，不执行简单的 `+1/-1`，而是重新查询数据库真实数量，再写 Redis。这样重复消息和乱序消息不会让计数不断漂移。

后台仍然会从 `ucnt:index` 抽样对账。

# 九、Outbox、Canal 与 Kafka

## 9.1 为什么需要 Outbox

如果业务代码采用：

```
提交 MySQL
→ 再发送 Kafka
```

可能出现：

```
MySQL 成功
→ 应用崩溃
→ Kafka 没有发送
```

下游永远不知道业务发生了变化。

Outbox 将两个动作放进同一个本地事务：

```
修改业务表
+ 插入 outbox
→ 一起提交或一起回滚
```

## 9.2 Canal 的位置

Spring Boot 不主动调用 Canal。

Canal 是独立运行的进程：

```
MySQL ROW Binlog
→ Canal 伪装成 MySQL 从库订阅
→ 过滤 zhiguang.outbox
→ Canal Kafka 模式发送 canal-outbox
```

因此 Spring Boot 配置中只有 Kafka Topic，没有 Canal 客户端配置是正常的。MySQL 地址、binlog 账号、表过滤和 Kafka 地址位于 Canal 外部配置。

## 9.3 消费者处理

同一个 `canal-outbox` Topic 包含多种 aggregate：

```
following
knowpost
```

消费者解析 Canal JSON 后，根据 `aggregate_type` 过滤：

- `relation-projection` 处理关系事件
    
- `feed-projection` 处理帖子事件
    

不同消费者组可以独立读取同一个 Topic。

## 9.4 事件只携带身份，不携带完整帖子快照

帖子事件主要包含：

```
postId
op
eventId
ts
```

消费者收到事件后重新查询 MySQL 当前状态。

这样即使事件积压、重复或顺序变化，消费者仍然以数据库最新状态投影，不会使用过期事件快照覆盖新状态。

# 十、Feed 系统

## 10.1 四种 Feed

|Feed|内容|排序|
|---|---|---|
|热门 Feed|已发布且公开|热门分数|
|我的主页|自己所有未删除帖子，包括草稿|创建时间|
|他人主页|public；已关注时增加 followers|创建时间|
|关注 Feed|已关注作者的 public 和 followers|创建时间合并|

## 10.2 Feed 的四类数据

### 排序索引

```
feed:author:{authorId}
feed:hot:candidates
feed:hot:public:{version}
feed:inbox:{userId}
```

### 大 V 拉取集合

```
feed:following:pull:{userId}
```

这里使用 Set，只保存当前用户关注的大 V 作者 ID。读取时再访问每个大 V 的作者 ZSet。

### 页面缓存

```
feed:page:{identity}
```

保存：

```
{
  "postIds": [],
  "nextCursor": "...",
  "hasMore": true
}
```

### 帖子分片

```
feed:item:{postId}
```

保存 Feed 卡片需要的稳定字段：

- 标题和摘要
    
- 标签和图片 URL
    
- 作者昵称和头像
    
- 状态和可见性
    
- 类型、置顶、创建时间、发布时间
    

不保存：

- 正文
    
- 正文 URL
    
- 点赞数、收藏数
    
- 当前用户是否点赞收藏
    

## 10.3 三级缓存

### L1：Caffeine 页面缓存

当前代码只缓存页面快照：

```
最大 20000 项
TTL 30 秒
```

### L2：Redis 页面缓存

```
Redis String + JSON
TTL 120～150 秒
```

### L3：Redis 帖子分片

```
feed:item:{postId}
TTL 7200～7800 秒
```

分片缺失时批量查询 MySQL，再写回 Redis。

ZSet 排序索引是页面缓存未命中后的候选数据源，它与三级页面/分片缓存共同组成 Feed 查询体系。

## 10.4 页面缓存解决的问题

页面缓存不只是省去一次 ZSet 查询，它缓存了整个查询阶段的结果：

```
多路索引合并
→ 去重
→ 状态过滤
→ 权限过滤
→ 凑够一页
→ 计算下一页游标
```

同一页面被重复访问时，可以直接拿到已经排好顺序的帖子 ID。

帖子详情仍从分片缓存读取，因此页面和帖子信息可以采用不同 TTL。

## 10.5 版本号

页面 Key 包含版本号，实现逻辑失效。

作者版本：

```
feed:version:author:{authorId}
```

帖子创建、修改、发布、删除时自增。

关注版本：

```
feed:version:following:{userId}
```

关注关系变化、普通作者投递帖子时自增。

大 V 全局版本：

```
feed:big-v:epoch
```

大 V 发布或修改帖子时增加，避免为数百万粉丝逐个修改版本。

版本变化后，新请求使用新页面 Key，旧页面等待 TTL 自动删除，不需要扫描和删除所有旧页面。

## 10.6 游标分页

时间 Feed 的游标包含：

```
score = createTime
postId
```

热门 Feed 还包含：

```
version
score = hotScore
postId
```

下一页条件：

```
score < cursor.score
或者
score == cursor.score 且 postId < cursor.postId
```

`postId` 是同分数时的稳定排序补充，避免时间相同造成重复或遗漏。

游标使用 JSON 序列化后再进行 URL Safe Base64 编码。它是不透明分页状态，不是权限凭证。

## 10.7 作者主页 Feed

作者索引：

```
feed:author:{authorId}
member = postId
score = createTime
```

索引保存作者所有未删除帖子。

读取时根据访问者决定过滤规则：

```
作者本人：所有未删除帖子
已关注者：published + public/followers
普通访问者：published + public
```

一个作者只维护一份 ZSet，在读取阶段完成权限过滤，避免为不同权限维护多份重复索引。

索引不存在时：

```
Redisson 加锁
→ MySQL 查询作者全部未删除帖子
→ 重建 ZSet
→ 加 __INIT__
→ TTL 7 天
```

## 10.8 关注 Feed 的推拉结合

普通作者采用推模式：

```
普通作者发布帖子
→ 查询粉丝 ID
→ 将 postId 写入每个粉丝的 feed:inbox
→ 收件箱最多保留 1000 条
```

优点是读取快，适合粉丝数量有限的作者。

大 V 采用拉模式：

```
用户关注大 V
→ 大 V ID 保存到 feed:following:pull:{userId}

读取关注 Feed
→ 读取普通作者 inbox
→ 获取关注的大 V ID
→ 读取每个大 V 的作者 ZSet
→ 多路合并、排序和去重
```

这样大 V 发一篇帖子时不需要向数百万个粉丝写入数据。

大 V 阈值当前为：

```
10000 粉丝
```

## 10.9 热门 Feed

候选池：

```
feed:hot:candidates
```

主要包含最近 30 天公开且已发布的帖子，重建时最多读取 20000 个候选。

每分钟重建一次榜单：

```
Redisson 抢锁
→ 获取候选 ID
→ 批量获取帖子分片
→ 批量获取点赞数和收藏数
→ 过滤非公开或非已发布帖子
→ 计算热门分数
→ 写入新的版本化 ZSet
→ 旧版本保留 30 分钟
→ 更新 current-version
```

当前公式：

```
interaction = likeCount × 3 + favoriteCount × 5 + 1

hotScore =
interaction / (ageHours + 2)^1.5
```

旧热门版本保留一段时间，是为了让用户继续使用原游标翻页，避免翻页过程中榜单变化造成大量重复和跳动。

## 10.10 一次完整 Feed 查询

```
根据 Feed 类型确定 scope、version、cursor
→ 组成 pageKey
→ 查询 Caffeine 页面缓存
→ 未命中查询 Redis 页面缓存
→ 页面缓存仍未命中
→ 从相应 ZSet 获取候选
→ 批量读取帖子分片
→ 根据状态和权限过滤
→ 不够一页则继续向后扫描
→ 生成 nextCursor 和 hasMore
→ 写 Redis 页面缓存和 Caffeine
→ 批量获取点赞数和收藏数
→ Pipeline 获取用户点赞收藏状态
→ 组装 FeedItemResponse
```

即使页面缓存命中，`hydrate` 仍会重新检查帖子分片和权限，避免页面缓存直接绕过最新的帖子可见性。

# 十三、当前代码必须先修复的问题

## 13.1 密码重置没有真正写数据库

[UserServiceImpl.java](file:///D:/JavaProjects/zhiguang/src/main/java/com/zhiguang/user/service/impl/UserServiceImpl.java:58) 的 `updatePassword` 是空方法。

结果：

```
接口返回成功
→ Refresh Token 被撤销
→ 但数据库密码没有变化
```

应调用 `userMapper.updatePassword(user)`。

## 13.2 取消点赞和取消收藏没有落库

[CounterEventConsumer.java](file:///D:/JavaProjects/zhiguang/src/main/java/com/zhiguang/counter/event/CounterEventConsumer.java:57) 没有判断 `delta`，所有事件都进入 `batchInsertIgnore`。

结果：

```
delta = -1
→ 消费者仍然 INSERT
→ like_record 中的记录不会删除
→ MySQL 真值错误
→ 缓存重建和对账都会得到错误结果
```

消费者必须按事件顺序处理 `delta=1` 和 `delta=-1`，或者按用户、帖子、类型合并出最终状态后分别批量插入和删除。

## 13.3 置顶和可见性的 Mapper 参数顺序传反

[KnowpostServiceImpl.java](file:///D:/JavaProjects/zhiguang/src/main/java/com/zhiguang/knowpost/service/impl/KnowpostServiceImpl.java:133) 调用了：

```
updateTop(creatorId, id, isTop)
```

Mapper 定义顺序是：

```
updateTop(id, creatorId, isTop)
```

`updateVisibility` 存在相同问题。

结果通常是更新行数为零，接口误报“草稿不存在或无权限”。

## 13.4 读取帖子详情会产生 Outbox 写入

[KnowpostServiceImpl.java](file:///D:/JavaProjects/zhiguang/src/main/java/com/zhiguang/knowpost/service/impl/KnowpostServiceImpl.java:215) 在 GET 详情过程中调用 `writeFeedEvent`。

结果：

```
每次浏览详情
→ 插入一条 outbox
→ Canal 发 Kafka
→ Feed 全链路重新投影
→ 普通作者还可能向全部粉丝执行 ZADD
```

GET 查询不应制造 Feed 变更事件。

## 13.5 关系计数对账的 Lua 语法错误

[RelationCounterReconcileTask.java](file:///D:/JavaProjects/zhiguang/src/main/java/com/zhiguang/relation/task/RelationCounterReconcileTask.java:49) 的 Lua 文本中使用了：

```
/* ... */
```

Redis Lua 只支持：

```
-- 单行注释
```

当前定时对账执行到脚本时会失败。

## 13.6 点赞对账可能释放未持有的锁

[CounterReconcileTask.java](file:///D:/JavaProjects/zhiguang/src/main/java/com/zhiguang/counter/task/CounterReconcileTask.java:66) 无条件执行 `lock.unlock()`。

如果本实例没有抢到锁，会抛出 `IllegalMonitorStateException`。应记录 `locked` 并检查 `isHeldByCurrentThread()`。

## 13.7 Refresh Token 可以被当作业务 Bearer Token

当前资源服务器只验证 JWT 签名和过期时间，没有在过滤链中要求：

```
token_type == access
```

Refresh Token 也携带 `uid`，因此可能访问需要登录的业务接口。需要给 `JwtDecoder` 增加 issuer 和 token_type 校验器。

## 13.8 用户资料查询尚未实现

[ProfileServiceImpl.java](file:///D:/JavaProjects/zhiguang/src/main/java/com/zhiguang/profile/service/impl/ProfileServiceImpl.java:23) 的 `getById` 固定返回 `Optional.empty()`，Controller 也没有用户资料 GET 接口。

如果产品需要打开用户主页并查询作者资料，这部分仍然缺失。

## 13.9 Feed 的大 V 身份切换存在投影空洞

作者从普通作者跨过 10000 粉丝后：

```
新帖子停止推送 inbox
→ 已关注他的老用户 pullAuthors 中可能还没有该作者
→ 这些用户可能看不到作者的新帖子
```

需要在大 V 身份变化时迁移关系投影，或者维护稳定的大 V 身份并发送“大 V 状态变化事件”。

## 13.10 热门榜为空时会反复重建

热门榜没有帖子时不会创建实际 ZSet Key，但 `currentVersion()` 又要求该 Key 存在，因此空站点可能每次请求都重新构建热门榜。

可以给空榜增加占位成员。

## 13.11 认证并发原子性不足

- 验证码发送间隔采用 `GET + SET`，并发下可能同时通过
    
- 验证码错误次数采用读取 Hash 后再写入，无法完全限制并发尝试
    
- Refresh Token 采用“检查后删除”，并发刷新可能同时成功
    
- `revokeAll` 使用 Redis `KEYS`，用户令牌较多时会阻塞 Redis
    

这些操作适合改为 Lua 原子脚本，并为 Refresh Token 维护用户级 Set 索引。

## 13.12 密钥与配置安全

- RSA 私钥存放在 `src/main/resources/keys/private.pem`
    
- 数据库和 Redis 密码直接写在 `application.yaml`
    
- 之前提供过的 OSS AccessKey 已经出现在会话中
    

OSS AccessKey 应立即在阿里云控制台轮换。私钥和中间件密码应改为环境变量或本地未提交配置。
