#### Q1:以“用户发布一篇知识内容”为例，从前端发起请求到数据持久化，再到首页 Feed 展示，完整链路是怎样的？
```
以用户发布一篇帖子为例，整个流程可以分为草稿创建、文件上传、元数据保存、正式发布和 Feed 展示五个阶段。

第一步是创建草稿。用户登录后，前端会携带 JWT 访问令牌，请求创建草稿接口。请求首先经过 Spring Security，由资源服务器完成 JWT 签名和有效期校验。Controller 从 JWT 中解析出用户 ID，Service 使用雪花算法生成内容 ID，然后通过 MyBatis 向 MySQL 的 `know_posts` 表插入一条记录。此时内容状态是 `draft`，默认类型是图文，默认可见范围是公开。先创建草稿的好处是，后续上传的正文和图片都可以绑定到一个确定的内容 ID 上。

第二步是上传正文和图片。对于每个文件，前端先请求 OSS 预签名接口。后端会校验草稿是否属于当前用户，然后根据内容 ID 生成对象存储路径，并返回一个有效期为十分钟的 PUT 预签名 URL。前端拿到 URL 后直接把文件上传到阿里云 OSS，文件数据不经过应用服务器，从而降低服务器的网络带宽和内存压力。

正文在前端会被封装成 Markdown 文件。上传之前，前端还会计算文件大小和 SHA-256；上传成功后获取 ETag，然后调用内容确认接口。后端将 `objectKey`、ETag、文件大小、SHA-256 和公共访问地址写入 MySQL。这样数据库保存的是文件元数据和访问地址，真正的大文本和图片保存在 OSS 中。

第三步是保存文章元数据。前端调用更新接口，将标题、标签、图片地址、内容摘要和可见范围等信息写入 `know_posts` 表。更新时会校验内容 ID 与当前用户的归属关系，避免用户修改其他人的草稿。同时，服务会写入一条 Outbox 事件，用于后续更新 Elasticsearch 搜索索引。

第四步是正式发布。前端调用发布接口，后端在事务中把内容状态从 `draft` 修改为 `published`，并写入 `publish_time`。同时更新用户的发文计数，并向 Outbox 表写入一条发布事件。MySQL 提交后，Canal 监听 Outbox 表的 binlog，将事件发送到 Kafka，搜索消费者再根据内容 ID从 MySQL查询完整数据并更新 Elasticsearch。这个过程主要负责搜索索引的最终一致性，不阻塞用户的发布请求。

发布完成后，系统还会为公开文章预先建立 RAG 向量索引，把文章内容分块并写入 Elasticsearch 向量库，从而减少用户第一次进行知识问答时的等待时间。即使搜索或 RAG 索引暂时失败，也不应该影响文章在 MySQL 中的正常发布。

第五步是首页 Feed 展示。客户端请求公开 Feed 接口时不强制要求登录，但如果携带了 JWT，系统会额外返回当前用户是否点赞、是否收藏等个性化状态。

Feed 查询采用多级缓存。首先查询本机的 Caffeine 页面缓存；如果没有命中，再根据页面对应的 ID 列表、内容片段和计数信息从 Redis 组装结果。Redis 中的共享内容不保存具体用户的点赞、收藏状态，用户状态会在返回前单独查询并叠加，避免不同用户之间的数据互相污染。

如果 Caffeine 和 Redis 都没有命中，系统会使用单飞机制控制并发，同一页面在同一时刻只允许一个请求回源 MySQL。数据库只查询 `status=published` 且 `visible=public` 的内容，并按照发布时间倒序排列。查询时会多取一条记录判断是否还有下一页，然后从 Redis 计数系统补充点赞数、收藏数，再把页面 ID 列表、内容片段和分页信息写入 Redis，并把页面结果写入 Caffeine，最后返回给前端。

因此，这条链路可以概括为：

用户请求创建草稿 → MySQL生成草稿记录 → 后端生成OSS预签名地址 → 前端直传正文和图片 → 回传文件元数据 → 保存标题、标签和摘要 → MySQL完成正式发布 → Outbox、Canal和Kafka异步更新搜索索引 → Feed通过Caffeine、Redis和MySQL三级查询返回内容。

这套设计的核心思路是：MySQL负责内容状态和元数据的可靠持久化，OSS负责大文件存储，Redis和Caffeine负责高频读取，Outbox、Canal和Kafka负责异步数据同步，Elasticsearch负责搜索和RAG检索。
```
