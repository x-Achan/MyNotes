
## 1. 关注数和粉丝数 

读：

```
1. 先读 Redis
2. Redis 命中，直接返回
3. Redis 未命中，查询 MySQL COUNT
4. 将结果写回 Redis
5. 返回数据库结果
```

写：

```
1. MySQL 事务内写 following 和 outbox
2. Canal 读取 outbox Binlog
3. Canal 将事件发送到 Kafka
4. RelationEventConsumer 消费事件
5. 根据 following 表重新计算真实关注数和粉丝数
6. 覆盖写入 Redis
```


## 2. 关注列表和粉丝列表

```
1. 读取 Redis ZSet
2. 刷新 TTL
3. 按 start、end 分页读取
4. 缓存不存在时加分布式锁
5. 获取锁后双重检查 Redis
6. 仍未命中时查询 MySQL 分页
7. 每次加载固定数量，例如 30 条
8. 写入 ZSet 后返回结果
```

关注或取关事件到达消费者后，删除相关 ZSet：

```
关注：
删除关注者的关注列表缓存
删除被关注者的粉丝列表缓存

取关：
删除对应的两个列表缓存
```

下一次读取时再从 MySQL 懒重建

## 4. 对账自愈

对账只针对关注数和粉丝数，不对账列表 ZSet

```
1. 从 Redis 的 ucnt:index 抽样计数键
2. 读取 Redis 当前计数
3. 根据 following 表计算数据库真实值
4. 计算 Redis 值与真实值的差值
5. 使用 Lua 脚本原子修正 Redis
6. Redis Key 已过期时，从索引中移除
```

对账使用分布式锁，避免多个应用实例同时修正

```
Kafka 消息丢失
Canal 暂停
消费者异常
Redis 数据被误删
Redis 与数据库长期不一致
```

## 5. 职责划分

```
MySQL：关系和状态的唯一真相源

Redis ZSet：关注列表和粉丝列表的部分缓存

Redis String：关注数和粉丝数缓存

Kafka：异步传播关系变更事件

TTL：列表缓存的失效兜底

定期对账：关注数和粉丝数的最终自愈机制
```
