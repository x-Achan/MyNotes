
### 实现功能：
- 用户点赞/收藏帖子
- 查询某条帖子的在点赞/收藏数
MySQL、Redis、Kafka、Lu
# 1. 数据模型

MySQL 的 `like_record`是唯一真相源，靠 `uk_user_post_type` 唯一键保证幂等，另外两个索引分别支撑 `COUNT(*)` 和个人主页的"我的点赞列表"。

Redis 里放三样东西：
- 一个是位图 `bitmap:knowpost:{帖子ID}:like:{分片}`，存"谁赞过"，用 `用户ID / 32768` 算分片、`% 32768` 算片内偏移，一个赞只占 1 bit
- 另一个是 `cnt:knowpost:{帖子ID}:like`，存"有多少赞"，专门给读路径用，O(1) 就能拿到。为什么计数不直接从位图算？ 因为 `BITCOUNT` 要扫所有分片，亿级赞的帖子大约 3000 个分片、12MB，单次读要十几毫秒，而读 `cnt` 是 0.1 毫秒——差一百倍以上，所以位图算总数只能用在重建和对账上
- 最后一个是索引集合set，记录当前所有cnt的key，用来对账自愈

# 2. 写路径
顺序是：
- 先用一个 Lua 脚本对位图做原子切换，一次调用同时拿到"幂等"（重复点赞返回 0）和"changed 标志"（只有状态真的翻转才算一次有效行为）
- 然后同步发一条 Kafka 事件，分区键用帖子 ID，保证同一个帖子的加减事件落到同一个分区、顺序不乱，并且等 `acks=all` 确认才返回——因为如果异步发送时进程崩了，明细会少一行而计数已经加了，这种"偏大"是对账修不了的；发事件失败我会补偿回滚位图，避免出现"位图说赞过、但明细和计数都没有"的悬挂状态
- 最后用另一个 Lua 更新计数，这个脚本做的是"判断 key 是否存在 + 自增"，不能直接 `INCR`，因为 `INCR` 会把缺失当成 0，而且会把 key 创建出来，导致后面的懒重建永远不触发，计数就永久错了

# 3.  Kafka 消费端批量异步落库

>真正的瓶颈是 `like_record` 唯一索引上的 gap 锁竞争——唯一索引插入要做重复键检查会加共享锁，和并发插入的插入意向锁冲突）
- 消费端把一批事件在内存里组装成多行，用一次多值 INSERT 写进数据库，再配合 JDBC 的 `rewriteBatchedStatements`；
- 200 次单条插入变成 1 次批量插入，锁等待从 238 降到 0，总耗时从 721ms 降到 35ms。因为计数已经在同步路径加过了，消费端只写明细，而明细靠唯一键 + `INSERT IGNORE` 天然幂等，所以连 eventId 去重都不需要

# 4. 对账 + 自愈

>因为懒重建只在 key 缺失时触发，修不了"存在但错"的值
- 对账定时从 `cnt:index` 这个索引集合里随机抽样（而不是用 `KEYS` 全库扫），比对 `cnt` 和 `COUNT(*)`，用差值 `INCRBY` 而不是 `SET` 覆盖修正——因为 `SET` 是绝对操作会覆盖对账期间的并发写入，差值会自然叠加。
- 这里有两个我自己踩出来的细节：一是修正本身必须原子，"读-算-写"分三步的话，两个并发对账会各补一次差值、叠加成过度修正，所以我把读、比较、修正全放进一个 Lua；
- 二是要设一个在途容忍上限，因为明细是异步落库的，落库没追上时 `cnt` 比 `COUNT(*)` 大是正常现象，直接修会把正确的计数改小，所以差值在容忍范围内就跳过，超出上限才判定为真错误。多实例部署时用 Redisson 分布式锁保证只有一台在对账。

# 5. 这套的边界
- 它只适用于允许最终一致的场景，余额、库存这种强一致的用不了；
- 另外位图是帖子维度的，答不了"我赞过哪些帖子"，那个查询走 MySQL 加索引；
- 如果将来单篇帖子成为热点、把 `cnt` 这一个 key 打满，就要上分片计数器
