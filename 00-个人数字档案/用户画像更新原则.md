# 用户画像更新原则

> 作用：本文件用于约束《个人 AI 技术画像》的更新方式，避免用户画像被随意扩写、重复记录、过度规划或被 AI 错误推断。任何 AI 工具在更新用户画像前，应先遵守本原则。

---

## 1. 用户画像的定位

用户画像不是日记、不是学习笔记、不是实验记录、不是任务清单。

用户画像只记录以下内容：

1. 用户的长期背景
2. 用户的核心目标
3. 用户的真实能力水平
4. 用户当前主要方向
5. 用户偏好的 AI 协作方式
6. 对后续规划有长期参考价值的信息

以下内容不应直接写入用户画像：

1. 每日学习流水账
2. 单次 LeetCode 题解
3. 单次实验日志
4. 临时情绪和短期想法
5. 未验证的 AI 猜测
6. 过细的代码修改记录
7. 已经失效的临时任务

---

## 2. 更新总原则

更新用户画像时，应遵守以下原则：

```text
真实 > 完整 > 简洁 > 可执行
```

具体要求：

1. 只记录真实发生或用户明确确认的信息。
2. 不为了显得厉害而美化能力水平。
3. 不把 AI 的推测当作事实。
4. 不把临时计划写成长期目标。
5. 不重复记录同一信息。
6. 不把画像写得过于臃肿。
7. 每次更新都要能帮助后续 AI 更好理解用户。

---

## 3. 可以更新用户画像的情况

当出现以下情况时，可以更新用户画像：

### 3.1 基本信息发生变化

例如：

- 年级变化
- 实习状态变化
- 研究方向变化
- 毕业目标变化
- 求职目标变化

### 3.2 技术能力发生明显变化

例如：

- 学完 Spring Boot 并能完成接口开发
- 能独立完成 MySQL 表设计和 CRUD
- LeetCode 中等题开始能独立完成
- 能独立跑通深度学习训练代码
- 能独立分析 loss、mAP、可视化结果

### 3.3 项目经历发生变化

例如：

- 完成了新的 Java 后端项目
- 项目部署上线
- 项目写入简历
- 项目被用于面试
- 项目技术栈发生重大变化

### 3.4 科研阶段发生变化

例如：

- 数据集准备完成
- baseline 跑通
- mAP 达到可信水平
- 完成消融实验
- 形成创新点
- 开始写论文
- 投稿或录用

### 3.5 AI 协作方式发生变化

例如：

- 开始固定使用 Claude Code 维护科研项目
- 建立了稳定的 Obsidian 工作流
- 改变了 AI 分工方式
- 新增长期使用的工具

---

## 4. 不应该更新用户画像的情况

以下内容不应写入用户画像，而应放入对应文件：

| 内容               | 应放入文件     |
| ---------------- | --------- |
| 每日学习内容           | 每日/每周复盘   |
| LeetCode 单题笔记    | 力扣刷题笔记    |
| 题型总结             | 题型模板笔记    |
| 单次科研训练结果         | 科研实验记录    |
| Claude Code 单次修改 | AI 协作记录   |
| Java 某个知识点笔记     | Java 学习笔记 |
| 临时任务安排           | 当前阶段任务看板  |
| 简历某一版修改          | 简历版本记录    |

原则：

```text
用户画像记录长期状态，其他文件记录过程细节。
```

## 5. 信息可信度分级

更新画像时，应区分信息来源和可信度。

### 5.1 用户明确说明

可信度最高。可以直接写入。

示例：

```text
用户说明：Spring Boot 当前为 0 分。
画像记录：Spring Boot：0，尚未学习。
```

### 5.2 公开作品或代码仓库体现

可信度较高，但应谨慎表述。

示例：

```text
GitHub 有 TankGame 项目。
画像记录：有 Java 桌面小游戏项目经历，可体现 Java OOP 和基础项目实践。
```

不能直接夸大为：

```text
具备成熟 Java 项目开发能力。
```

### 5.3 AI 推断

只能作为“判断”或“推测”，不能写成事实。

示例：

```text
当前判断：该项目可作为 Java 基础实践项目，但不适合作为 Java 后端核心项目。
```

### 5.4 未验证实验结果

不能写成结论，只能写成待验证假设。

示例：

```text
Claude Code 估计修改后预测准确率可能提升到约 30%，但尚未经过完整训练和评估验证。
```

不能写成：

```text
模型准确率已达到 30%。
```

## 6. 能力评分更新规则

用户画像中的能力评分采用 0-4 分：

```text
0 = 没学过
1 = 看过但不会写
2 = 能写简单代码 / 能做简单实践
3 = 比较熟 / 能独立完成常规任务
4 = 能讲清楚原理并用于项目或实验
```

更新能力评分时，必须满足以下规则：

1. 不能只因为“看了视频”就提高评分。
2. 不能只因为“AI 帮我写了代码”就提高评分。
3. 必须有可验证产出，才能提高评分。
4. 用户能够独立解释核心原理，评分才可能达到 3 或 4。
5. 能力退化或长期未使用，也可以下调评分。

### 6.1 Java 后端评分示例

Spring Boot 从 0 提到 2，需要满足：

- 能创建 Spring Boot 项目
- 能写 Controller 接口
- 能处理请求参数
- 能返回统一结果
- 能本地运行和测试接口

Spring Boot 从 2 提到 3，需要满足：

- 能结合 MySQL / MyBatis 完成完整业务模块
- 能处理异常、参数校验、分层结构
- 能独立排查常见 bug

### 6.2 算法评分示例

Hot 100 基础题型从“较弱”更新为“入门掌握”，需要满足：

- 相关题型至少完成多道代表题
- 有统一笔记
- 能说出题型识别依据
- 相似题能独立写出核心思路

### 6.3 科研实验能力评分示例

PyTorch 从 2 提到 3，需要满足：

- 能读懂训练流程
- 能修改模型或数据加载相关代码
- 能理解 loss 变化
- 能根据日志和可视化结果定位常见问题
- 能独立完成一次有记录的实验

## 7. 版本管理规则

用户画像应使用版本号管理。

建议格式：

```text
个人 AI 技术画像 v0.1
个人 AI 技术画像 v0.2
个人 AI 技术画像 v0.3
...
```

### 7.1 什么时候升级小版本

以下情况升级小版本：

- 补充了一批新的真实信息
- 更新了某个能力模块
- 新增了项目或科研阶段信息
- 调整了 AI 协作方式

示例：

```text
v0.4 → v0.5
```

### 7.2 什么时候升级大版本

以下情况可以升级大版本：

- 拿到第一份 Java 实习
- 完成第一个可写入简历的 Java 后端项目
- 科研 baseline 跑通并形成稳定实验系统
- 论文进入投稿阶段
- 求职方向发生明显变化

示例：

```text
v0.x → v1.0
```

## 8. 更新记录规则

每次更新画像时，应在文件末尾添加更新记录。

模板：

```md
## 更新记录

### v0.x - 日期

更新内容：

1. 
2. 
3. 

信息来源：

- 用户明确说明
- 公开仓库/博客
- AI 根据已有信息判断

待确认信息：

1. 
2. 
```

---

## 9. 待确认信息规则

如果某个信息不确定，不要强行写成事实。

应写入“待确认”部分。

示例：

```md
## 待确认信息

- 是否接受外包实习
- 是否接受北京线下日常实习
- AI 简历分析系统是否完全由本人独立开发
- 当前科研训练命令和配置文件
```

待确认信息被用户确认后，再移动到正式画像对应部分。

## 10. 画像与其他文件的边界

### 10.1 用户画像负责回答

```text
我是谁？
我要什么？
我现在什么水平？
我当前主线是什么？
AI 应该如何帮助我？
```

### 10.2 当前阶段任务看板负责回答

```text
我现在正在做什么？
下一步任务是什么？
完成标准是什么？
```

### 10.3 学习笔记负责回答

```text
某个知识点是什么？
我怎么理解它？
有哪些代码例子？
```

### 10.4 刷题笔记负责回答

```text
这道题怎么做？
属于什么题型？
我错在哪里？
下次如何迁移？
```

### 10.5 科研实验记录负责回答

```text
这次实验改了什么？
怎么训练的？
结果如何？
是否可信？
下一步验证什么？
```

### 10.6 AI 协作记录负责回答

```text
AI 修改了什么代码？
为什么这样改？
我是否理解？
是否验证通过？
```

## 11. AI 更新画像时的操作流程

任何 AI 工具更新画像前，应按以下流程进行：

```text
读取当前画像
↓
判断新信息是否值得写入画像
↓
区分事实、推测、待确认
↓
更新对应模块
↓
避免重复和过度扩写
↓
更新版本号
↓
添加更新记录
↓
列出待确认信息
```

---

## 12. AI 更新画像时的固定 Prompt

以后可以把下面这段发给 AI：

```text
请根据我提供的新信息，更新《个人 AI 技术画像》。

更新要求：
1. 先判断哪些信息适合写入用户画像，哪些应该放入学习笔记、任务看板或实验记录。
2. 不要把临时任务、单次实验细节、单题题解写入画像。
3. 区分事实、AI 判断和待确认信息。
4. 不要美化我的能力水平。
5. 不要重复记录已有内容。
6. 更新版本号，并在末尾添加更新记录。
7. 如果信息不确定，放入“待确认信息”，不要写成事实。
```

---

## 13. 用户画像更新检查清单

每次更新前，检查以下问题：

```md
- [ ] 这条信息是否具有长期价值？
- [ ] 这条信息是否会影响后续规划？
- [ ] 这条信息是否由用户明确确认？
- [ ] 如果是 AI 推断，是否标注为判断？
- [ ] 是否有重复记录？
- [ ] 是否应该放到其他文件，而不是用户画像？
- [ ] 是否更新了版本号？
- [ ] 是否添加了更新记录？
```

---

## 14. 最重要的原则

用户画像的价值不在于写得多，而在于让 AI 快速理解用户，并给出适合用户当前阶段的帮助。

最终原则：

```text
用户画像要稳定，任务看板要动态，学习笔记要详细，实验记录要可复现。
```
