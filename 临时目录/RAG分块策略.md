
# 分块策略—RAG 效果差异最大的环节

分块（Chunking）是把长文档切成适合检索的小片段。这个步骤看起来很"工程"，实际上对 RAG 效果影响比大多数人想象的要大得多。鸡哥在项目里测过：同样的文档，换一种分块策略，检索命中率从 45% 提升到 78%。没有改模型，没有改检索算法，就改了怎么切。分块是 RAG 里性价比最高的优化点。

一、为什么要分块

你可能会想：直接把整篇文档向量化不行吗？不行，有两个原因：原因一：向量语义混杂，检索精度差。一份 50 页的产品手册，向量化成一个向量后，这个向量里同时包含了产品参数、安装步骤、故障排查、售后政策……用户问"故障排查怎么做"，这个混合向量和"故障排查"的语义匹配度只有 0.5，因为向量里还有大量无关内容。原因二：模型上下文窗口有限。即便上下文窗口很大，把整本手册塞进 Prompt 的 Token 成本非常高，而且模型对过长上下文的中间部分注意力会显著下降。分块的核心目标：每个块的语义尽量聚焦，一个块只讲一件事，检索时能精准命中。

二、块太大 vs 块太小的问题

通用建议：300-600 Token 是甜点区，在语义聚焦和上下文完整之间取得平衡。这不是死规则。法律文档需要更小的块（精准）；技术手册可以稍大（上下文完整）。后面针对不同文档类型会细说。

为什么需要重叠： 如果一个关键信息恰好在两块的边界处（比如"最高补偿金额为一万元"被切成了"最高补偿金额为"和"一万元，具体以合同为准"），有重叠就能保证至少一个块能完整包含这个信息。重叠区大小建议：块大小的 10-15%。

重叠区不是越大越好——过大的重叠区会让相邻块内容高度重复，检索时同一个问题会命中一堆说同一件事的块，浪费上下文窗口。

四、不同文档类型的分块策略

这才是实际工作中最有价值的部分。 不同文档类型有完全不同的最佳分块方式，套一个 TokenTextSplitter 通杀是不对的。技术文档 / 产品手册

按 Token 数量切，在段落边界切，保留上下文。块大小：500 Token重叠区：50-80 Token分块器：TokenTextSplitter（先在段落边界切，超出再按 Token 截）FAQ 文档（一问一答）

FAQ 是特殊场景——一个问题和对应的答案是一个完整的语义单元，绝对不能被切断。鸡哥见过一个很经典的失败：FAQ 文档按 500 Token 切，结果 Q3 的问题在第二块的末尾，答案在第三块的开头。用户问到 Q3 的问题，检索到的两个块拼起来才有完整答案，但模型经常只能看到一块，给出残缺回答。解法：按空行分段，一问一答一块，不管有多短。 FAQ 的每个 Q&A 就是一个完整的语义单元，这是文档的天然边界，比 Token 数量更重要。法律合同 / 政策文档

法律文件每句话都可能很关键，条款之间高度关联。块大小：300 Token（更小，语义更聚焦）重叠区：50 Token（偏大，防止条款被切断）注意：按条款编号切，不要在条款中间切断代码文档

代码的天然分割单位是函数和类，不是 Token 数量。按语法边界切，不要在函数中间截断。每个函数（含注释和函数签名）是一个块实在太长的函数可以按逻辑段落切，但不要切在赋值语句中间如果有代码解析能力（如 JavaParser），按 AST 精确分割效果最好表格 / 结构化内容

表格的每一行通常是一条独立记录，按行切。保留表头：每个块都带上列名，不然检索到的行没有语义格式转换：表格转成自然语言描述后再入库，向量检索效果更好"产品 XPro-3000，最大承载 500kg，工作温度 -20°C 至 80°C"这比直接存 XPro-3000 | 500kg | -20~80 向量语义更好

五、父子块检索（Parent-Child Chunking）

这是 Advanced RAG 里的重要技巧，解决块大小的根本矛盾：小块：向量语义聚焦，检索精度高大块：上下文完整，模型理解更好父子块策略：用小块检索，用大块喂给模型。

典型场景：技术手册里有一段介绍某个配置项。小块只包含配置项名称和一句描述，向量语义很聚焦，能精准检索。但模型回答时需要知道这个配置项的背景、适用场景、注意事项，这些在父块里。两全其美。

六、分块策略选型总结

|   |   |   |   |
|---|---|---|---|
|文档类型|推荐策略|块大小|重叠区|
|通用技术文档 / 产品手册|Token 切分，段落优先|500 Token|50-80|
|FAQ 问答|按空行分段，一问一答一块|不限|0|
|法律 / 政策 / 合同|Token 切分，按条款|300 Token|50|
|代码文档|按函数 / 类边界切|视代码长度|0|
|新闻 / 文章|Token 切分，段落优先|400 Token|50|
|表格 / 结构化内容|每行一块，含表头；或转自然语言|1-3 行|0|

七、常见坑

坑一：默认参数不改很多同学用 TokenTextSplitter(500, 50, ...) 就完事了，从来不看实际切出来的块是什么样。养成习惯：入库之前，打印前 10 个块，看看有没有明显截断或语义破碎的情况。坑二：忘记设相似度阈值入库时块切得多，查询时设了 TopK=5 但没设相似度阈值，低质量的块也会被返回。分块和检索参数是一起调的。坑三：文档更新时只增不删文档更新了旧版本，但旧块还在向量库里。结果检索会同时返回新旧两个版本的内容，模型搞混。文档更新时要同步删除旧块，按文档 ID 做精确替换。
